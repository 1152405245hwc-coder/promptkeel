# 破甲原理与可落地方案

这份文档回答两个问题：为什么拒答会发生，以及一个项目能对哪一层动手。所有结论都标注来源类型（`实测` = 本项目跑过，`论文` = 公开研究，`工程` = 同类项目做法）。

## 一、拒答发生在四个不同的位置

| 层 | 谁在拦截 | 我们能改吗 | 证据 |
| --- | --- | --- | --- |
| 供应商前置分类器 | 网关 / 服务商在请求进入模型前判定 | 改不了，只能换编码或换通道 | `实测`：`gpt-6.1-sol` 对勒索、撞库两类请求直接返回 `HTTP 400 safety filter: cyber_policy` |
| 模型对齐（RLHF / 宪法） | 模型权重与训练后的策略 | 只能挪概率，不能保证 | `实测`：同一套提示词下 DeepSeek 拒 2/4，GLM 拒 1/4 |
| 宿主叠加层 | 宿主自带的系统提示、审批、沙箱、会话警告 | 能改，本项目的主体 | `实测`：16 条补丁后 `probe 18/18`，本机 `adapt` 全 `ready` |
| 我们自己加的脚手架 | 我们写进提示词的"必须拒绝"句式 | 能改，且最容易犯 | `实测`：`detectRefusal` 漏判会把拒答统计成成功，已补 4 类句式 |

关键点：**破甲深度不是把一句话改狠，而是判断拒答来自哪一层**。对第一层用提示词是零收益；对第四层改一句话就够。

## 二、为什么模型侧会松动的公开解释

- 竞争目标（competing objectives）：有用性与安全性在训练中相互拉扯，越像"正常工作请求"，安全策略越难单独生效。Wei 等 2023《Jailbroken》把这归为 competing objectives 与 mismatched generalization 两类失效。
- 拒答是浅层行为（refusal direction）：Arditi 等 2024 发现拒答在激活空间里近似一个方向，抑制它即可改变行为。提示词层可用的等价手段是**把对话状态推到"已经在回答"的位置**——assistant prefill（预填助手开头）就是最直接的做法。
- 长上下文冲淡（many-shot）：Anthropic 2024 的 many-shot jailbreaking 表明，上下文里塞入大量"问题—服从回答"样例后，模型对后续请求的拒答率显著下降。
- 渐进升级（Crescendo）：微软 2024 的多轮方法，每一轮只比上一轮激进一点，单轮看都无害。
- 分词器缝隙（ArtPrompt / 编码族）：把敏感词拆成 ASCII art 或 base64，模型仍能解码但分类器看不到原词。
- 采样效应（Best-of-N）：同一提示做多次随机变体（大小写、空格、引号、前缀），成功率随样本数上升——这是最便宜也最被低估的一条。

来源类型均为 `论文`，方法名可在公开仓库检索；EasyJailbreak 把其中 12 种recipe 做成了可组合组件（Selector / Mutator / Constraint / Evaluator），DAN 与 L1B3RT4S 是 `工程` 侧的长期实践集合。

## 三、可以静态化的六种杠杆

| 杠杆 | 做法 | 本项目落点 | 代价 |
| --- | --- | --- | --- |
| 角色 | 给模型一个职业身份，让"专业职责"覆盖"通用谨慎" | `prompt/personas/roleplay.md`、`unfiltered.md` | 一次编译，零额外请求 |
| 预填 | 在 user 之后放一条 assistant 开头，把模型推到"正在交付"的状态 | `--ladder` 的 `prefill` 阶 | 每请求 +1 条消息 |
| 编码 | base64 / rot13 / 摩斯 / 分列，绕过词面分类 | `core/transform.mjs` + `--transform` | 提示词膨胀（摩斯对 CJK 约 22 倍） |
| 嵌套 | 场景里套场景，外层框架承担"这是虚构"的说明 | `prompt/personas/nested.md` | 零额外请求，但更依赖模型合作 |
| 少样本 | 若干条"按要求交付"的示例对话 | `prompt/personas/fewshot.md`；many-shot 需多轮 | 上下文成本高 |
| 多轮渐进 | 每轮只前进一步 | 尚未实现（`live_matrix` 目前单轮） | 请求数 × 轮数 |

## 四、阶梯：把杠杆排成成本递增的顺序

四阶，先便宜后贵，命中即停：

1. `direct` —— 只用宿主提示（基线）。
2. `persona` —— 加 `unfiltered` 人设，零额外请求。
3. `cipher` —— base64 编码，绕过词面分类。
4. `prefill` —— `unfiltered` + assistant 预填，把对话推进到"已经在写"。

这样每个 (模型, 探针) 得到一个"第几阶解决"的读数，比单一成功率更能说明该模型吃哪一套。`--ladder` 就是这四阶；`--control` 仍可叠加，用来区分"提示词起效"和"模型本来就不拒"。

## 五、不建议做的事

- 梯度类攻击（GCG 后缀）：需要白盒梯度，对闭源 API 无效，且后缀脆弱、跨模型不迁移。
- 大量 many-shot 灌上下文：单次成本高、易触发上下文异常，收益不如 prefill。
- 把每一层都用上：编码 + 嵌套 + 多轮同时开，失败时无法归因。阶梯的意义就是每步只动一个变量。

## 六、本项目的边界

`probe` 测的是**提示词本身**（是否残留身份、是否有拒答脚手架、编码是否可逆），不测模型意愿；`live_matrix` 测的是**真实调用结果**，但每格一次采样，只说明那一分钟的表现。两者都不能承诺"某模型必定放行"。
